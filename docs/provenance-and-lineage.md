# Provenance and Transformation Profile

## Why a shared profile is needed

Existing repositories already capture valuable but different evidence: payload hash chains, release hashes, workflow identity, licence status, dataset cards and publication manifests. The missing layer is a common semantic contract that lets a downstream research object answer, without manual reconstruction:

- Which exact source versions contributed to this result?
- When were they published, effective, retrieved and transformed?
- Which code, model, ontology, command and parameters were used?
- Which records or partitions were affected by a change?
- Which quality checks passed, failed or were waived, and why?
- What may be redistributed, under which attribution and restrictions?
- Can the output be rebuilt and byte-compared or semantically compared?

## Native event model

The event log is append only. Each event has:

```text
event_id, stream_id, sequence
occurred_at, recorded_at
event_type, status
activity
agents[]
inputs[]
outputs[]
parameters
environment
schemas[] and classifications[]
rights_assertions[]
quality_evidence[]
previous_event_hash, event_hash
```

The schema is in `schemas/provenance-event.schema.json`.

## Event types

- `source.discovered`
- `source.metadata_snapshot`
- `capture.started`, `capture.completed`, `capture.failed`
- `artifact.verified`
- `transformation.started`, `transformation.completed`, `transformation.failed`
- `validation.completed`
- `snapshot.assembled`, `snapshot.revised`
- `materialization.created`
- `publication.staged`, `publication.released`
- `rights.reviewed`
- `governance.reviewed`

## Granularity policy

### Level A — artifact lineage (mandatory)

Every file/object/distribution is linked to the run that generated it and the artifacts used.

### Level B — layer/partition lineage (mandatory for spatial and large datasets)

Each output layer, tile set, partition or logical table identifies contributing source layers/partitions and transformation rule sets.

### Level C — feature/row lineage (conditional)

Capture when source records have durable identifiers and the operation is one-to-one, filtered, aggregated with a stored membership map, or otherwise reproducible. Do not generate enormous pseudo-precise graphs for joins or probabilistic entity resolution without a clear query need.

For probabilistic reconciliation, store candidate links, scores, decision rules, reviewer actions and model versions.

## Transformation record

A completed transformation identifies:

- versioned implementation (`repository`, `commit`, optional `swhid`);
- package lockfile and container/environment digest;
- invocation command and normalised parameters;
- input artifact identities and schema versions;
- output artifact identities and schema versions;
- start/end times and execution agent;
- deterministic/non-deterministic classification and random seeds;
- warnings, exclusions and failure/partial status;
- quality checks generated by the run.

## Manual activity

Manual decisions are first-class activities. A correction, classification, mapping or exclusion must record:

- reviewer identity or role;
- input evidence;
- decision and reason;
- decision policy/version;
- time;
- affected entities;
- whether dual review or adjudication occurred.

## Event hashing

Canonical event hashing excludes the `event_hash` field and serialises JSON with sorted keys and compact separators. `previous_event_hash` creates a tamper-evident stream. Release attestations sign the manifest and event-stream digest.

## Bitemporal requirements

Retrieval time answers “when did we acquire it?”; valid/effective time answers “when did it apply?” These are not interchangeable. For council planning data, capture at least:

- source publication timestamp if exposed;
- service `lastEditDate` or equivalent if exposed;
- retrieval timestamp;
- plan status (`proposed`, `appeals`, `operative`, `partly operative`, etc.) as a sourced assertion;
- operative/effective date where explicitly evidenced;
- supersession/revocation date where explicitly evidenced.

Each assertion retains its source and confidence.

## Reproducibility classes

| Class | Meaning |
|---|---|
| R0 | evidence preserved; transformation not executable |
| R1 | executable with documented environment; output not expected byte-identical |
| R2 | deterministic semantic rebuild; canonical records compare equal |
| R3 | byte-reproducible build/materialisation |
| R4 | independently reproduced from original sources and compared |

A release reports the achieved class per materialisation, not one aspirational project-wide label.
